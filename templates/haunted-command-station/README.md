# Haunted command station

A starting point for Track 2, The Haunted Dashboard. Messy, real-time "Spooky Incident Logs" go in; a working tactical command station comes out, generated by a model and streamed to the browser over WebSockets, panel by panel. The alerts it raises go to Slack and Linear.

Every refresh (two minutes by default):

1. **Pull.** New incident lines from the local log generator (or `LOGS_URL`), plus live web reports from You.com Search through One.
2. **Think.** A CrewAI crew on Parasail, in order: the **Structurer** turns raw lines into JSON incidents, the **Designer** decides what a commander needs to see, and the **Builder** asks a Parasail model for the JSON UI spec (`response_format={"type": "json_object"}`).
3. **Check.** `spec.validate` drops anything the page cannot render and fills in any required panel the model left out, so the page never goes blank.
4. **Stream.** The server pushes the spec over a WebSocket, one panel at a time. The page renders a threat map, an activity chart, the top alerts, a stats row and the web results.
5. **Act.** Through One, the top three alerts go to Slack (only when they change) and the worst one becomes a Linear issue (once per incident).

## The four tools

| Tool | What it does here |
|---|---|
| You.com | Live web reports for `INCIDENT_QUERY` on every refresh: Search (`GET /v1/search`) on One's `you` platform |
| One | Every app call, through the One CLI with one key: You.com search, Slack `chat.postMessage`, Linear `issueCreate`. Action ids are resolved at run time |
| CrewAI | Runs the Structurer, Designer and Builder as a sequential crew |
| Parasail | Runs all three agents, and the JSON-mode call that generates the UI spec |

## Setup

Node 22.23.4+, 24.22.1+ or 26.12.1+ (the One CLI and MCP server refuse older releases; setup checks), One CLI 2.9+, Python 3.10 to 3.13 (setup picks 3.13 or 3.12 if you have them), a One account, a Parasail key, and three connections:

```bash
one add you      # key from https://api.you.com
one add slack    # then invite the bot to your channel
one add linear

cd templates/haunted-command-station
./setup.sh       # creates .venv and .env; fill .env in, then run ./setup.sh again
```

Fill in `.env`:

- `PARASAIL_API_KEY` from https://www.saas.parasail.io/keys
- `PARASAIL_MODEL`, default `parasail-kimi-k26`
- `ONE_SECRET` from https://app.withone.ai/settings/api-keys
- `SLACK_CHANNEL` (a channel id like `C0123...`) and `LINEAR_TEAM_KEY` (the short key, like `ENG`)
- the `ONE_*_CONNECTION_KEY` lines only if you have more than one connection for that platform

The second `./setup.sh` runs `python main.py --check`: it confirms the Parasail model exists for your key, that each platform is connected, and that the Linear team resolves. It also writes `.onerc` so the One CLI only sees these three connections.

### Picking a Parasail model

The Builder agent calls a tool, so the model must support tool (function) calling, and the spec step needs JSON mode. Model ids change; list the ones your key can use:

```bash
curl -s https://api.parasail.io/v1/models -H "Authorization: Bearer $PARASAIL_API_KEY" | jq -r '.data[].id'
```

`parasail-kimi-k26` is the default. `parasail-deepseek-v4-flash`, `parasail-qwen3p6-35b-a3b` and `parasail-glm-52` also list tool calling in Parasail's docs (https://docs.parasail.io/parasail-docs/guides/tool-function-calling.md). A faster model makes the station refresh faster.

`parasail.py` builds the CrewAI LLM as `LLM(model=<id>, provider="openai", base_url="https://api.parasail.io/v1", api_key=...)`. Use `provider="openai"` with the bare id, not `model="openai/<id>"`: in crewai 1.15.2 the prefix form only works for model names CrewAI already knows, and anything else falls through to LiteLLM, which plain `crewai` does not install.

## Run

```bash
source .venv/bin/activate
python main.py --offline    # no keys at all: local logs and a spec built without a model. Good for working on the page
python main.py --dry-run    # Parasail and You.com, but Slack and Linear writes are printed, not sent
python main.py              # live: alerts to SLACK_CHANNEL, the worst one filed in LINEAR_TEAM_KEY
python main.py --once       # build one spec, then keep serving it (no refresh loop)
python incident_logs.py --stream   # just watch the raw logs
```

Open http://127.0.0.1:8765. `--port`, `--interval` and `--seed` (a repeatable log stream for demos) are there when you need them.

## What you will see

In the browser: a header with the threat level, then panels appearing one at a time as the spec streams in. A stats row, a 3 by 3 threat map of the sectors (quiet to critical, each with a text label), a per-minute activity chart by incident type (hover for values, or open the table view), the top alerts worst first, and the You.com results as links. On the right, the pipeline's status and the raw log lines as they arrive.

In the terminal, `python main.py --offline --once --seed 7` prints this (a `--dry-run` or live run adds the crew stages and the You.com line):

```text
Offline: local logs, no model, no One. Slack and Linear writes are printed.
Station on http://127.0.0.1:8765  (WebSocket ws://127.0.0.1:8765/ws)
  Pipeline: refresh started
  Logs: 7 new line(s) from the local generator, 7 in the window
  Station: streamed 4 panel(s), threat high, built by offline fallback (no model)
  [dry-run] Slack #station:
    *Haunted command station: threat HIGH*
    :warning: [serious] Clocktower: Zombie activity level 6 in Clocktower
    :warning: [serious] Clocktower: Phantom activity level 6 in Clocktower
    :ghost: [warning] Clocktower: Zombie activity level 5 in Clocktower
    Live station: http://127.0.0.1:8765
  [dry-run] Linear issue: [serious] Clocktower: Zombie activity level 6 in Clocktower
  One: Slack posted, Linear filed DRY-RUN
Built once (--once). Still serving; Ctrl-C to stop.
```

A live run sends that Slack message to your channel and files the Linear issue, then on later refreshes posts again only when the top alerts change, and files again only for a new worst incident. It remembers what it sent in `out/state.json`, so a restart does not repeat itself. A dry run keeps its own `out/state.dry-run.json`, so a rehearsal never stops the real run from filing.

## How it is built

- `main.py` runs the refresh loop in a worker thread and the server on the event loop.
- `incident_logs.py` generates the Spooky Incident Logs: radio chatter, sensor dumps and citizen reports across nine sectors, with one sector escalating over time. `LOGS_URL` swaps in a real feed (plain text lines, or a JSON array of strings or objects with a `line`).
- `crew.py` is the Structurer, Designer and Builder. The Builder has one tool, `build_ui_spec`, which makes the JSON-mode Parasail call. If the agent skips its tool, the code makes the call itself.
- `spec.py` is the spec schema, `validate`, and `fallback` (the no-model spec used offline and whenever the crew fails).
- `server.py` serves the page, `/spec.json` and the `/ws` stream on one port, with the `websockets` library.
- `static/index.html` renders the spec with vanilla JS and inline SVG. No build step. Every string from the model is set as text, never as HTML, and only `http(s)` links are rendered.
- `one_actions.py` holds the One calls: You.com search, the Slack post, the Linear issue. A write that times out is reported and never retried blindly (see `WriteUncertain` in `one_cli.py`).
- `parasail.py` is the model helper (shared with the Track 1 template). `one_cli.py` is the One CLI helper (shared with the Track 1 template; it finds every action id in one `one actions find` call).

The WebSocket protocol is documented at the top of `server.py`: `log`, `status`, `spec_begin`, `panel`, `spec_end`, plus a full `spec` for a client that connects late (or, mid-stream, the panels sent so far, so nothing shows twice).

## How to extend

- Let the model invent panels. Add a type to `spec.py` (`_clean_panel`) and a renderer to `index.html`, and tell the Builder about it in `BUILDER_SYSTEM`.
- Read the page behind a search hit with You.com's Get Web Page Contents through One, and let the Structurer extract incidents from the full article.
- Make the station interactive: send a message up the WebSocket ("focus Pier 13") and have the next refresh build around it.
- Add a daily brief: a scheduled run that emails the day's worst incidents through One's `gmail` platform.
